## The rule for this phase

**`as` is not a fix. It's a silencer.**

```ts
const email = formData.get("email") as string;   // ❌ lying to the compiler
```

That compiles. At runtime, if the field is a file upload, `email` is a `File` and your
next line crashes. The `as` didn't make it a string — it stopped TypeScript telling you
it might not be.

**Narrow instead of casting:**

```ts
const raw = formData.get("email");
if (typeof raw !== "string") return { error: "..." };
// TypeScript now KNOWS raw is a string — because you checked
```

## Problem 1 — Route params: stop hand-writing the type

**Goal:** params typed from the **actual folder structure**, so renaming a folder
breaks the build.

**Files:** every `app/**/[*]/page.tsx`

### The thing nobody tells you: Next 16 generates these for you

You've been writing this all track:

```tsx
type PageProps = { params: Promise<{ slug: string }> };
export default async function BlogPost({ params }: PageProps) { ... }
```

Next 16 generates a **global** `PageProps<'/route'>` type from your folder tree. No
import needed:

```tsx
export default async function BlogPost(props: PageProps<"/blog/[slug]">) {
  const { slug } = await props.params;
}
```

The generated map is derived from your actual routes — look at
`.next/types/routes.d.ts` after a build:

```ts
"/blog/[slug]":                          { "slug": string; }
"/docs/[[...slug]]":                     { "slug"?: string[]; }
"/products/[id]/variants/[variantId]":   { "id": string; "variantId": string; }
```

There's a matching `LayoutProps<'/route'>` for layouts, which also types any parallel
route slots.

### Why this beats the hand-written version

A hand-written type is a **claim**. The generated one is **derived**. Both mistakes
below are caught only by the generated version — measured:

```
Wrong param name:
  TS2339: Property 'postId' does not exist on type '{ slug: string; }'

Route string that doesn't exist:
  TS2344: Type '"/blog/[nope]"' does not satisfy the constraint 'AppRoutes'
```

Remember Phase 5 Problem 6, where you had to reconcile `[id]` against `[productId]` by
hand? With `PageProps<'/products/[id]'>` the rename would have failed the build
instead.

### Build

1. Convert every dynamic page to `PageProps<'/the/[route]'>`
2. Convert layouts that read params to `LayoutProps<'/the/route'>`
3. Delete the now-unused hand-written `type PageProps = ...` declarations
4. **Then** deliberately mistype a param name and a route string, and read both errors

> [!warning] The types are generated by a build
> If `PageProps` is unknown, run `npm run build` (or `next dev`) once to generate
> `.next/types/`. Deleting `.next` removes them until the next build.

### Still write the three shapes by hand once

You need to be able to do this in an interview without a build step:

```
[id]        ->  { params: Promise<{ id: string }> }
[...slug]   ->  { params: Promise<{ slug: string[] }> }
[[...slug]] ->  { params: Promise<{ slug?: string[] }> }
```

The `?` on the third is the type system encoding "bare `/docs` is a valid URL".

## Problem 2 — Type API responses, and find the hole

**Goal:** one response shape across every endpoint — then discover it stops at the
network.

**Files:** `lib/api.ts` *(extend)*, `app/api/**/route.ts`

### Build

1. Upgrade Phase 8's `ApiError` into a discriminated union:
   ```ts
   export type ApiResponse<T> =
     | { success: true; data: T }
     | { success: false; error: string };
   ```
2. Use it for every endpoint's body
3. Type handlers as returning `Promise<Response>`
4. **Comment** that `Response.json()` doesn't carry the body type, and show how
   `NextResponse.json<T>()` differs
5. **Then find the hole:** in a Client Component, `fetch` one of your own endpoints and
   hover over `await res.json()`

### What a discriminated union buys you

Two shapes sharing a literal field that tells them apart. Once you check
`if (result.success)`, TypeScript **narrows** to that branch — `.data` is reachable
only on success, `.error` only on failure. You cannot read the wrong one.

### Step 5 is the real lesson

`res.json()` returns **`any`**. Always. Your server types stop dead at the network
boundary — types are compile-time only, and nothing survives being serialised to JSON
and parsed back.

Three ways to close it:

1. A runtime validator (Zod or similar) that parses **and** types
2. A hand-written type guard
3. A shared schema both sides generate from

`as ApiResponse<Product>` is **not** one of them — same lie as before.

You met this already in Phase 11 Problem 1, where swapping `getProducts()` for
`fetch()` made `items` untyped.

## Problem 3 — Type form actions

**Goal:** no `as string` anywhere near `FormData`.

**Files:** `lib/form.ts` *(from Phase 10)*, `app/actions/*.ts`

### Build

1. Confirm `FormState` from Phase 10 is the single shared shape
2. Type every action `(prevState: FormState, formData: FormData) => Promise<FormState>`
3. **Find every `as string` on a `formData.get()`** and replace it with narrowing
4. Extract the repetition into a helper:
   ```ts
   export function getString(form: FormData, key: string): string | null
   ```
5. **Test it:** pass `formData.get("email")` straight into a `string` parameter

### What you need to know

`formData.get()` returns `FormDataEntryValue | null`, and `FormDataEntryValue` is
`string | File`.

**The `File` case is not theoretical.** Any `<input type="file">` produces one — and
Server Actions are public HTTP endpoints, so anyone can send whatever they like.

`null` is the other case: the field simply wasn't submitted.

### Verify

Passing `formData.get("email")` into a `string` parameter is a **compile error**. Zero
`as string` on FormData in the codebase.

## Problem 4 — Type Server Component props

**Goal:** correct return types on async components.

**Files:** async pages and layouts

### Build

1. Let async components **infer** their return type — don't annotate `JSX.Element`
2. If you annotate at all, it's `Promise<React.ReactNode>`
3. `children` is `React.ReactNode`, never `JSX.Element`
4. Write **one** generic Server Component:
   ```tsx
   function List<T>({ items, render }: {
     items: T[];
     render: (item: T) => React.ReactNode;
   })
   ```
5. **Test it:** annotate an async component as returning `JSX.Element`

### What you need to know

An `async function` returns a **Promise**. So an async component returns
`Promise<ReactNode>`, not `ReactNode`. Annotating `JSX.Element` is simply wrong about
what the function returns.

React's types **historically didn't allow** async components at all — you'd get
*"'Page' cannot be used as a JSX component"*. That was a types-lag problem, fixed in
React 19's types. This app runs React 19.2.8, so you won't hit it, but you will in
older codebases.

`React.ReactNode` covers elements, strings, numbers, arrays, null. `JSX.Element` covers
only a single element — so it **rejects a valid string child**.

## Problem 5 — Type Client Component props

**Goal:** make non-serializable props impossible to pass.

**Files:** every `"use client"` component receiving server data

### Build

1. Type each one's props explicitly
2. Confirm no prop type is `Date`, `Map`, `Set`, or a plain function
3. Add one **event handler** prop defined client-side — that's fine
4. Type a **Server Action** passed as a prop — that one **is** allowed
5. **Test both directions:** try typing a prop as `Date`, and try passing a plain
   callback from a Server Component

### What you need to know

Props crossing the boundary are **serialized** — JSON, over the wire, rebuilt in the
browser. Survivors: strings, numbers, booleans, null, arrays, plain objects, Promises.

Casualties: `Date`, `Map`, `Set`, class instances, functions.

**Why Server Actions are the exception.** They aren't sent as code. Next replaces the
function with a **reference id**, and the client gets a stub that makes an HTTP request
back when called. The function never crosses — only its address does.

This is why `lib/types.ts` keeps `createdAt` as a `string`, and why `RecentOrder.placedAt`
is a string too. You hit both in Phase 3 Problem 5 and Phase 4 Problem 7.

## Problem 6 — Type query parameters, once

**Goal:** one helper module replacing every ad-hoc `searchParams` parse.

**File:** `lib/params.ts` *(new)*

### Build

```ts
export type SearchParams = Promise<{
  [key: string]: string | string[] | undefined;
}>;

export function single(v: string | string[] | undefined): string | undefined
export function toInt(v: string | string[] | undefined, fallback: number, max?: number): number
```

1. `single` — narrow the array case to one value
2. `toInt` — parse with a default and an upper bound; handle `NaN`, negatives, zero
3. Decide the repeated-param policy: first, last, or reject
4. **Then replace every inline parse in the app** — Phase 5's category route, Phase 6's
   pagination, Phase 9's sort, Phase 12's homepage

### You've now written this five times

`single` and `toInt` already exist, copy-pasted, in at least
`app/(shop)/shop/[category]/page.tsx` and `app/(shop)/products/(list)/page.tsx`. That
duplication is the point — you only feel it after living with it.

### The behaviour to preserve

Measured earlier, and worth keeping as tests in a comment:

| URL | `toInt(v, 1)` | why |
|---|---|---|
| `?page=3` | 3 | normal |
| *(absent)* | 1 | `NaN` |
| `?page=abc` | 1 | `NaN` |
| `?page=0` | 1 | below 1 |
| `?page=1.5` | 1 | not an integer |
| `?page=` | 1 | **`Number("") is 0`** — caught by the `< 1` half |
| `?page=99999` | 100 | clamped |
| `?page=2&page=9` | 2 | first wins |

> [!warning] The guard needs **both** halves
> `Number("")` is `0`, not `NaN` — so `Number.isInteger` lets it through and only
> `< 1` stops it. Drop either check and something slips past.

## Problem 7 — Type the session

**Goal:** the null case is impossible to forget.

**File:** `lib/session.ts` *(from Phase 12)*

### Build

1. Confirm `Session.role` is the **literal union** `Role`, never `string`
2. `getSession(): Promise<Session | null>`
3. `requireSession(): Promise<Session>`
4. A **type guard** validating a decoded token really is a `Session`:
   ```ts
   function isSession(value: unknown): value is Session
   ```
   Check **every field** — it came from outside your program.
5. **Test it:** use `getSession()`'s result without a null check

### Why two functions, not one

The return types carry the meaning:

| Signature | Caller must | Right for |
|---|---|---|
| `Promise<Session \| null>` | handle null | public pages |
| `Promise<Session>` | nothing | protected pages |

One nullable function would force pointless null checks on protected pages.

### Why the type guard matters most here

A decoded token is `unknown` — it came from a cookie, possibly forged. `value is Session`
is a **type predicate**: TypeScript trusts your check and narrows afterwards. So this is
the one place where getting the logic right actually matters. Validate every field;
don't just check for null.

`role: string` would let `"admni"` compile and silently never match any role check. The
literal union catches it at build time.
